# Financial safety model

- Money is represented as decimal strings/`Decimal`; currencies are never aggregated without a verified FX conversion.
- An original transfer status other than documented failure is not replacement eligibility. Unknown/unmapped statuses block recovery.
- Persisted transfer evidence omits free-text provider failure messages and keeps only validated structured failure/reason codes. A `CANCELLED` status is mapped to confirmed failure only when such a code is present; a message alone stays unknown and requires escalation/refresh.
- `FAILED` is a confirmed Airwallex failure state; it still does not authorize an automatic replacement.
- A local operation identifier is not described as Airwallex idempotency. Transfer `request_id` support is documented for seven days; after a write timeout, reconcile by that same request ID and never issue a new request while unresolved.
- The internal operation service persists the exact same-currency, saved-beneficiary recovery parameters and stable Airwallex `request_id` before submission, and binds them to a verified original's amount, currency, beneficiary ID, and method. The original evidence must be no older than five minutes at preparation time. A database unique index allows only one durable recovery reservation per original transfer, including across multiple incident records. An empty lookup remains unknown; a conflicting or multiple match escalates; one exact match proceeds only to a separate retrieval verification state.
- The internal approval service binds a five-minute approval to the full prepared request hash, verified original evidence version, and current treasury policy version. Approval requires a separate policy-admin role; submission consumes the approval once and rechecks freshness and binding. This service is unit-tested but is not exposed through an application route, and the deployed/local operator identity is still role-based rather than named-user SSO.
- Airwallex's direct transfer validate endpoint checks request schema but does not return a fee quote; the create response reports the fee. The separate Batch Transfers API documents quoting a draft batch before submission, including fee and payer/beneficiary amounts. Its item also needs a beneficiary and payer form; TreasuryPilot has no payer-contact lookup or configured payer ID. The batch route first creates and modifies a draft resource, and account support, one-item behavior, payer/corridor schema, quote expiry handling, and cleanup are unverified. TreasuryPilot has not implemented or tested the batch quote lifecycle, so the current live recovery workflow still blocks when fee impact is unknown.
- No real write is available without sandbox credentials, a verified beneficiary schema, an eligible failed transfer, fresh live balance, policy pass, and action-bound approval.
- The Airwallex read adapter rejects any base URL other than `https://api.sandbox.airwallex.com`; credentials cannot accidentally direct this build to a production host.
- Supplier obligations entered in the dashboard are stored with `operator_entered` provenance and audit events. They are not verified against an invoice/payables source or Airwallex and cannot independently authorize a payment.
- Saved-beneficiary refresh is available only after a verified Airwallex transfer provides the beneficiary ID. The API records a minimized response and omits account-holder name, account number, routing details, and address. Retrieval does not prove beneficiary ownership or authorize a payment.
- Production treasury policy changes require a distinct `APP_ADMIN_TOKEN`; the ordinary operator token receives HTTP 403. Local development keeps a single-operator shortcut. Policy audit rows record the `admin` role, while incident and recovery evaluation records capture the authenticated role. The approval service independently requires the admin role and will not accept the requester's role as approver.
- Live treasury plans use a fresh read-only balance snapshot, matching currency policy, and operator-entered obligations. The calculation accepts fees per obligation so one route's fee cannot be reused for another supplier; it does not verify fee provenance, action binding, or expiry. The current API has no quote lifecycle to supply those verified values, so all live obligations remain held for unknown fees. Unknown fees also leave post-payment projections unset. Plans and source snapshots are persisted for audit, but do not initiate transfers.
- Synthetic demonstration data is visibly identified and never presented as bank evidence.
